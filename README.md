# Цифровая НИС

Защищённая платформа целевых расчётов в цифровых рублях для
сделок приобретения жилья военнослужащими в рамках
накопительно-ипотечной системы (НИС).

Прототип моделирует полный цикл расчётной операции:
эмиссию окрашенного расчётного токена → блокировку в смарт-контракте
эскроу → верификацию подписанного подтверждения оракула Росреестра →
зачисление средств застройщику с автоматическим возвратом при срыве
сделки. Криптография — по стандартам РФ: ГОСТ Р 34.11-2012 (Стрибог),
ГОСТ Р 34.10-2012 (ЭЦП), ГОСТ Р 34.12-2015 (Кузнечик + MGM).

## Статус и назначение

**Модельный прототип.** Внутренние токены системы представляют
расчётные обязательства в демонстрационной модели и **не являются
цифровыми рублями, выпущенными Банком России**. Эмитент
(Росвоенипотека) выступает условным инициатором целевой выплаты.
Интеграция с реальной платформой цифрового рубля не реализована.

**Границы применимости.** Система охватывает только расчётный
этап — момент перевода средств от военнослужащего к застройщику.
Этапы получения свидетельства, одобрения ипотеки и выбора объекта
система не затрагивает.

## Архитектура

### Слои и зависимости

```text
cmd/nis-node          cmd/oracle-rosreestr        cmd/auditor-cli
     │                        │                        │
     ▼                        ▼                        ▼
internal/app            internal/oracle          internal/audit
     │                        │                        │
     ├────────────────────────┼────────────────────────┤
     ▼                        ▼                        ▼
internal/engine  ◄──── internal/crypto ────►  internal/security
     │
     ▼
internal/ledger
```

Направление зависимостей — строго сверху вниз. Пакет `internal/engine`
объявляет интерфейс `Ledger`, пакет `internal/ledger` его реализует.
Это разрывает циклическую зависимость и позволяет заменить BadgerDB
на Hyperledger Fabric или другую СУБД без изменения бизнес-логики.

### Роли и мандаты

| Роль | Допустимые операции |
|---|---|
| `emitter` | эмиссия окрашенного токена |
| `oracle` | колбэк оракула с подписанным подтверждением |
| `user` | инициация сделки, чтение собственных контрактов |
| `auditor` | чтение `merkle_root` и статусов безопасности |
| `admin` | все операции |

Проверка ролей реализована в middleware на каждый эндпоинт.
Запросы аутентифицируются через Zero Trust конверт либо (в demo-режиме)
через заголовок `X-NIS-Demo-Role`.

### Модель токена

Каждый токен несёт криптографический тег целевого назначения:

```text
TargetColorTag = hex(Стрибог-256(ИНН_застройщика || ":" || КадастрNo))
```

Подпись эмитента покрывает **все существенные поля токена** через
каноническую сериализацию с длинами полей:

```text
v1|issuer|len:TokenID|len:Amount|len:ColorTag|len:MilitaryHash|
    len:INN|len:Kadastr|len:IssuedAt|len:MaxLockDuration
```

Это исключает подмену суммы, получателя или срока без потери
валидности подписи.

### Trigger раскрытия эскроу

Система поддерживает два сценария:

- `REGISTRATION` — раскрытие после регистрации права собственности
  покупателя (сценарий **готового жилья**);
- `RVE` — раскрытие после получения разрешения на ввод объекта
  в эксплуатацию (сценарий **долевого строительства по 214-ФЗ**).

Trigger входит в digest подписи оракула и в структуру контракта.
Несовпадение триггера в колбэке и в контракте отклоняется с ошибкой
`ErrTokenMisuse`.

### Защита идентификатора военнослужащего

`militaryIDHash` формируется на узле с использованием **HMAC на основе
Стрибога** (Р 50.1.113-2016) от внутреннего идентификатора. Секретный
ключ HMAC хранится на узле. Без ключа перебрать `militaryIDHash`
невозможно.

Внутренний ID нигде не сохраняется — только результат HMAC.

## API узла

| Метод | Путь | Роль | Описание |
|---|---|---|---|
| GET  | `/healthz` | — | Проверка живости |
| POST | `/api/v1/issue` | emitter, admin | Эмиссия окрашенного токена |
| POST | `/api/v1/lock` | user, admin | Блокировка в эскроу |
| POST | `/api/v1/rosreestr/callback` | oracle, admin | Обработка колбэка оракула |
| GET  | `/api/v1/escrow/{dealID}` | user (свой), auditor, admin | Чтение контракта |
| POST | `/api/v1/demo/run` | admin | Полный прогон сделки |
| GET  | `/api/v1/security/status` | auditor, admin | Сводка и `merkle_root` |

**Rate limiting:** 100 запросов в минуту с одного IP.

**Пример запроса `/api/v1/demo/run`:**

```json
{
  "amount": 485000000,
  "military_internal_id": "internal-id-001",
  "developer_inn": "7701982341",
  "kadastr": "77:01:0001001:102",
  "trigger": "REGISTRATION",
  "reject": false
}
```

Поле `deal_id` необязательно — узел сгенерирует криптостойкий
идентификатор, если оно не передано.

## CLI-аудитор

Три команды.

Полный аудит с публикацией якоря:

```bash
./bin/auditor-cli -db ./data/nis-state -cmd full-audit -publish
```

Строит Merkle-дерево по всем контрактам, выводит корневой хэш,
сравнивает с последним якорем, при флаге `-publish` записывает
новый якорь в append-only журнал `data/audit-anchors.jsonl`.

Проверка против последнего якоря:

```bash
./bin/auditor-cli -db ./data/nis-state -cmd verify-anchor
```

Возвращает `СОВПАДАЕТ` — реестр не изменён или `РАСХОЖДЕНИЕ` — данные изменены.

Доказательство включения конкретной сделки:

```bash
./bin/auditor-cli -db ./data/nis-state -cmd prove -deal DEAL-...
```

Строит путь от листа к корню и верифицирует его.

**Зачем нужен внешний якорь.** Совпадение корневых хэшей у CLI и
HTTP API доказывает только согласованность вычислений. Чтобы
подтвердить неизменность, корень сравнивается с ранее сохранённым
в независимом журнале — если атакующий подменит всю базу, новый
корень не совпадёт с якорем.

### Аудит при работающем узле

BadgerDB блокирует файлы БД на время работы узла. Параллельный аудит
возможен:

- **Linux/macOS:** с флагом `-read-only` — аудитор открывает БД
  без блокировки.
- **Windows:** только при остановленном узле или на копии БД
  (read-only режим в BadgerDB на Windows не поддерживается).

Пример на Windows:

```powershell
Copy-Item -Recurse -Force .\data\nis-state .\data\nis-state-audit
.\bin\auditor-cli.exe -db .\data\nis-state-audit -cmd full-audit -publish
```

## Быстрый старт

### Зависимости

- Go 1.21+ (проверено на 1.26)
- Node.js 18+ (для дашборда)
- BadgerDB и остальные зависимости подтягиваются через `go mod tidy`

### Сборка

```bash
go mod tidy
go build -o ./bin/nis-node ./cmd/nis-node
go build -o ./bin/oracle-rosreestr ./cmd/oracle-rosreestr
go build -o ./bin/auditor-cli ./cmd/auditor-cli
```

### Демо-прогон (offline)

```bash
./bin/nis-node -config ./configs/node-smolensk.yaml -demo
```

Система создаст контракт, эмулирует ответ оракула локально,
завершит сделку и выведет финальное состояние.

### Сквозной сценарий через HTTP

Терминал 1 — оракул Росреестра:

```bash
./bin/oracle-rosreestr -config ./configs/oracle-mock.yaml
```

При первом запуске оракул сгенерирует ключи и выведет их. Скопируйте
приватный ключ в `configs/oracle-mock.yaml`, а публичный — в
`configs/node-smolensk.yaml`.

Терминал 2 — узел в серверном режиме:

```bash
./bin/nis-node -config ./configs/node-smolensk.yaml
```

Узел поднимется на `:8080` и запустит фоновый worker автовозврата.

### Дашборд

```bash
cd web
npm install
npm run dev
```

Открыть http://localhost:5173.

## Безопасность

### Что реализовано

- ГОСТ Р 34.11-2012 (Стрибог-256/512) — хэширование, Merkle-дерево,
  каноническая сериализация.
- ГОСТ Р 34.10-2012 — ЭЦП эмитента и оракула на эллиптических
  кривых.
- ГОСТ Р 34.12-2015 (Кузнечик + MGM AEAD) — шифрование с
  аутентификацией в Zero Trust контуре.
- HMAC на основе Стрибога (Р 50.1.113-2016) — защита
  идентификатора военнослужащего от перебора.
- Zero Trust конверт — идентификатор узла, роль, метка времени,
  nonce, хэш payload, ГОСТ-подпись. Nonce фиксируется только после
  успешной проверки подписи.
- mTLS — двусторонняя аутентификация между узлом и оракулом.
- RBAC — роли и middleware на каждый эндпоинт.
- Проверка владения объектом — пользователь видит только свои
  контракты.
- Rate limiting — 100 запросов в минуту на IP.
- Внешний якорь Merkle-root — append-only журнал для
  доказательства неизменности реестра.
- Криптостойкие DealID — генерируются через Стрибог от случайных
  данных.

### Проверенные негативные сценарии

Во всех случаях система отклоняет операцию и не изменяет
состояние реестра.

| Угроза | Реакция |
|---|---|
| Подмена тега окрашивания | `ErrTokenMisuse` |
| Подмена ИНН или кадастра | `ErrTokenMisuse` |
| Подмена суммы или срока в токене | `ErrIssuerSigInvalid` |
| Подмена подписи эмитента | `ErrIssuerSigInvalid` |
| Подмена подписи оракула | `ErrOracleSigInvalid` |
| Подмена триггера раскрытия | `ErrTokenMisuse` |
| Повторное использование tokenID | `ErrTokenAlreadyUsed` |
| Двойная блокировка по DealID | `ErrConflict` |
| Replay Zero Trust конверта | `ErrReplayNonce` |
| Подмена payload в конверте | `ErrPayloadHash` |
| Использование неизвестного узла | `ErrUnknownNode` |
| Роль в конверте не совпадает с зарегистрированной | `ErrRoleMismatch` |
| Чтение чужого контракта пользователем | HTTP 403 |
| Tamper с доказательством Merkle | Отказ верификации |
| Превышение rate limit | HTTP 429 |

## Ограничения прототипа

- Открытая ГОСТ-библиотека (`bi-zone/ruwireguard-go`) не
  сертифицирована ФСБ. Для промышленной эксплуатации требуется
  замена на КриптоПро CSP или ViPNet через CGO.
- mTLS вместо ГОСТ TLS. Стандартный TLS 1.3 с ECDSA-сертификатами.
  Прикладная криптография — реальная ГОСТ-подпись на payload.
- Модель эскроу для сценария `REGISTRATION` (готовое жильё)
  не требует изменений в законе. Для сценария `RVE` (долевое
  строительство) необходимо согласование с действующим
  регулированием эскроу-счетов.
- Платёжный адаптер не реализован. Система фиксирует разрешение
  на выплату сменой статуса контракта, но не выполняет реальный
  перевод средств через платформу Банка России.

## Производительность

Стенд: AMD FX-6100 (6 ядер, 2011), Windows 10, Go 1.26, BadgerDB
embedded, открытая ГОСТ-библиотека без CGO.

| Режим | Полных циклов | TPS | p50 | p95 | p99 |
|---|---:|---:|---:|---:|---:|
| Последовательный | 500 | 45,7 | 21,5 мс | 27,0 мс | 29,5 мс |
| Параллельный (8 воркеров) | 200 | 49,0 | 161 мс | 183 мс | 186 мс |

**Интерпретация.** Полученные значения характеризуют
производительность прототипа в указанных условиях стендовых
испытаний. ГОСТ-криптография на эллиптических кривых не является
узким местом. Параллельный режим ограничен из-за вынужденной
сериализации подписей (открытая библиотека небезопасна при
параллельных операциях на одной кривой). При переходе на
сертифицированное СКЗИ мьютекс не нужен, и производительность
растёт линейно с числом ядер.

## Отладка в VS Code

- Открыть папку `digital-nis` как корень workspace.
- Конфигурации запуска (F5):
  - Узел: server mode — узел с HTTP API
  - Узел: demo mode — сквозной сценарий
  - Оракул Росреестра — сервис-эмулятор
  - Аудитор: full-audit — полный аудит реестра
  - Бенчмарки — последовательный и параллельный
  - Тесты: все пакеты
- Задачи (Ctrl+Shift+P → Tasks: Run Task): сборка, тесты, бенчмарки,
  аудит.

## Сборка под Astra Linux SE «Смоленск»

```bash
make astra
```

Соберёт статические бинарники с `CGO_ENABLED=0` для `linux/amd64`.
Не зависят от системного libc, готовы к развёртыванию в защищённом
контуре.

## Лицензия и зависимости

Проект использует открытые библиотеки:

- `github.com/bi-zone/ruwireguard-go` (GPL-3.0) — ГОСТ-криптография

Для научного и патентного использования лицензия GPL-3.0 не создаёт
проблем: патентное право защищает способ и алгоритм, а не код. Для
проприетарного продукта требуется юридическая экспертиза либо
замена на сертифицированное СКЗИ.
